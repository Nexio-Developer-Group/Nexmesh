# S7 review: paper-only and special-purpose items

Compared on documentation, feasibility and relevance. NOT ranked against S1-S6; no shared accuracy numbers. All claimed numbers are author claims, unverified, unless stated. Date 2026-10-23. CPU: shared 4-core VM (lscpu model not exposed to agent), 2 threads, CPU only.

## 1. YFS90 terrain-weighted geolocalisation (documentation review only)
- Sources: repo https://github.com/YFS90/GNSS-Denied-UAV-Geolocalization (HEAD 968eaf8, 2024-11-28, single commit line, branch `main` only, no tags); paper Yao, Lan, Wang, Wan, Gao, Wei, "GNSS-denied geolocalization of UAVs using terrain-weighted constraint optimization", Int. J. Applied Earth Observation and Geoinformation 135, 104277 (Dec 2024), doi 10.1016/j.jag.2024.104277. Full text was not retrievable here (ScienceDirect 403); the summary below uses the repo README and the published abstract, so it is high level.
- Plain-language method: the UAV image stream is (a) matched to publicly available satellite map tiles (the map is cut into chunks for memory management), (b) tracked frame to frame by visual odometry, and (c) a 2D-3D geo-registration step ("bidirectional homologous point search") lifts matched points to 3D "virtual control points" using public DEM terrain heights. A sliding-window optimisation then fuses matches and odometry, with each constraint weighted by terrain (so flat or featureless terrain is trusted less). Claimed to need no altimeter or IMU, no loop closure, no error accumulation, and to re-localise after a failure; also claimed to tolerate tilt, rotation, altitude change, season and light change.
- Code and weights: NONE. Verified: repo tree contains only README.md and Img/ (images, GIF, 20 result figures with bilibili/YouTube video links); `git ls-remote` shows only refs/heads/main; no tags or releases; README links no code, data or weights. The author's other public repo `Real-time-orthophoto` is a different paper (GPS-free orthophoto SLAM), not this system. We did not reimplement.
- Licence: no LICENSE file; all rights reserved by default, so reuse is not permitted. Paper is journal-published (check ScienceDirect access terms).
- Claimed data/results (unverified): 20 scenarios (plains, hills, urban, rural, multiple viewpoints, seasons, thermal infrared night); abstract claims mean absolute error under 7 m; README claims accuracy "comparable to GPS". No per-scenario table seen by us.
- Feasibility on Jetson Orin class: unknown; no runtime reported in the material we could read, and without code it cannot be tested; a reimplementation would be a multi-month project (VO + DEM registration + windowed optimisation).
- Relevance to NIDAR (200 m nadir, 1280x800 grey, 0.18 m/px): conceptually highly relevant (satellite matching plus VO plus no IMU need, absolute fixes with no drift), and DEM terrain weighting matters little over the flat Pune site. Currently unusable: nothing to run.
- Documentation rubric 0-3: install steps 0 (no code); config explained 0; results reproducible 0 (videos only); algorithm described 1 (README is a marketing summary; detail lives in the paywalled paper).

## 2. Bearing-UAV (CVPR 2026)
- Sources: paper "Beyond Matching to Tiles: Bridging Unaligned Aerial and Satellite Views for Vision-Only UAV Navigation", Liu et al., arXiv 2603.22153 (CVPR 2026); code https://github.com/liukejia121/bearinguav (HEAD d16e558, 2026-05-01); weights https://huggingface.co/HaoyZhou/bearinguav (Bearing_UAV.zip, 131 MB, ungated, no HF licence tag); dataset Bearing-UAV-90K on HF (single 6.3 GB zip, NOT downloaded; we read only the 225-row mini metadata and 3 sample blocks via HTTP range to learn the input format).
- Plain-language method: it is not a matcher. A VGG-16 backbone (frozen, ImageNet) plus a non-local/clustering head turns each of five 256x256 images into a descriptor: four satellite tiles forming a 2x2 block and one UAV patch. A relative-coordinate encoder, patch-similarity prior and cross-attention fuse them, and two regression heads output the UAV position inside the block and heading as (cos, sin). A "Bearing-Naver" scheme steps along waypoints using it. Needs a known starting block (prior), no map-wide search.
- Code/weights: both released. Licence Apache-2.0 (code); dataset/weights licence not stated. Weights run on CPU (about 133 ms per step in the paper on GPU; here median 4.4 s per sample on a loaded shared 4-core CPU at 2 threads).
- Claimed results (unverified, author claims, own Google-Earth-3D-rendered data): mean localisation error 8.61 m (7.48 m with weather aug), mean heading error 12.90 deg, Recall@1 83.2%, LSR@15 89.4%, HSR@15 77.2%; waypoint navigation success only about 50% (SR@20), navigation error 275 m. Model about 68 MB, 10.5 GFLOPs at 256x256.
- Our run (labelled SYNTHETIC NIDAR-like, out of distribution; results/s7/bearing/S7-B-20261023-s0/): driver `solutions/s7_paper_only/bearing_driver.py`. Four 64 m tiles cut from the Esri reference map (same map the video was rendered from, so optimistic) around an oracle block centre placed at truth plus a seeded random offset (+-0.9 units = +-29 m); UAV patch = central 64 m (356 px) crop of our frame resized to 256. 153 frames (1 Hz subset, seed 0). Metrics via harness/metrics.py summarize(): median position error 28.2 m, p95 48.8 m, RMSE 30.2 m, max 59.7 m, 100% "fix" rate (the model always answers). Trivial baseline "predict block centre" (the oracle prior itself): median 23.1 m, mean 22.2 m. So the model is NOT better than the prior here. Heading: median error 93.6 deg, mean 96.2 deg, i.e. chance level (random is about 90 deg); heading convention is assumed (see caveats), and the nadir 64 m crop of a straight-down 1280x800 image does not look like the paper's Google-Earth 3D rendered views.
- Sanity check of the code path (results/s7/sanity/dataset_samples.json): on 3 samples from the paper's own mini dataset the released weights give 3.9, 1.5, 1.6 m and 2.4, 11.2, 2.7 deg errors (3 samples only; may be training data; shows weights and driver load correctly).
- Caveats: tile geometry assumed contiguous 64 m tiles at p1..p4 = (-1,-1),(-1,+1),(+1,-1),(+1,+1) in (x east, y south) units of 32 m; the sample tiles looked non-contiguous so the real layout may differ; heading frame (image-up = heading) assumed; scale 0.25 m/px per 256 px assumed from README/config; the 64 m footprint is much narrower than our true 230x144 m footprint; sat tiles from different imagery source than training (Google Earth). The negative result therefore means "no evidence of use out of the box", not "the method cannot work".
- Feasibility on Jetson Orin class: yes, small VGG-16 style network (68 MB, 10.5 GFLOPs), likely tens of ms on Orin GPU; but needs retraining for our camera and a known-start block.
- Relevance to NIDAR: low-to-medium; designed for oblique/3D-rendered urban views with a known starting block, only about 50% waypoint success in its own paper, regression gives no confidence/inlier check; fine-tuning on NIDAR-like data would be needed (not done: instructed not to train).
- Documentation rubric 0-3: install steps 1 (README lists CUDA 11.8 / Python 3.9 pins; Python 3.13 and torch 2.1.2 not installable, we used py3.11 CPU torch 2.1.2; imgaug/albumentations imported at module load although unused for inference; ImageNet VGG16 weights silently downloaded at model build, 528 MB); config explained 2 (JSON config shipped with weights); results reproducible 1 (test script and weights exist but need the 6.3 GB zip and GPU-style paths, no inference-on-your-own-images example); algorithm described 2 (paper plus architecture tree; heading/tile conventions undocumented).
- Setup effort: about 45 min wall clock, 4 failed steps: (1) gh API access to repo denied (used add_repo then git clone), (2) pip torch 2.1.2 not available for Python 3.13 (used 3.11 venv), (3) two installs failed with "No space left on device" (shared disk dipped to 185 MB free; retried after space returned), (4) imgaug missing (stubbed). Env 1.4 GB, weights 262 MB (git-ignored).

## 3. STHN thermal homography
- Sources: repo https://github.com/arplaboratory/STHN (HEAD 0b44a84, 2026-05-16); paper Xiao, Zhang, Tortei, Loianno, IEEE RA-L 9(10) 2024, arXiv 2405.20470 (v3 Sep 2025); weights on HF: xjh19972/STHN (one_stage 6.5 MB, two_stages 12.3 MB safetensors) and xjh19972/STHN-one-stage; dataset (122 GB) NOT downloaded, as instructed.
- Plain-language method: given a thermal image from straight-down UAV camera and a larger satellite crop around the last known position, a CNN predicts how the four corners of the thermal image move to land on the satellite image (homography via DLT). Coarse stage: both images resized to 256 px, iterative correlation-based updates (6 iterations). Optional fine stage: crop the satellite image around the coarse result and refine. A pix2pix-style "thermal generative module" synthesises fake thermal images from satellite tiles to enlarge training data. The location is the image centre mapped into the satellite frame. Works within a 512 m search radius of the last known position, even with the thermal image only 11% the satellite size.
- Code/weights: both released. Licence MIT (code, LICENSE file "Copyright 2024 ARPL"); data/weights licence not stated. Demo script STHN_demo.py runs on one sample pair (needs conda env.yml, torch, kornia).
- Claimed results (unverified): MACE 12.70 m (two-stage, 512 m offset, 0% failures), 16.42 m (one-stage), localisation error 12.12 m at 63.9 ms on an RTX 2080 Ti; keypoint baselines fail 83-99.7%.
- Run: not run. Not applicable: models are trained for 8-bit thermal (Boson, about 1 m/px, night) and our payload is visible grayscale at 0.18 m/px, so a thermal-trained model would be out of domain; running it would not produce meaningful evidence. Weights existence verified by the HF listing only.
- Feasibility on Jetson Orin class: yes; tiny models (6.5-12 MB) and paper reports 64 ms on a desktop GPU.
- Relevance to NIDAR: not applicable to the visible payload; useful only if a thermal camera is ever added (night operation). The homography-regression idea (bounded search around last position, no dense tile search) is conceptually transferable, but would need retraining on visible-to-satellite pairs.
- Documentation rubric 0-3: install 2 (env.yml plus demo that pulls weights automatically); config explained 2 (scripts per setting, HF config.json); results reproducible 2 (weights, 122 GB data and train/eval scripts; slurm-oriented); algorithm described 3 (paper, README architecture notes, code links).
